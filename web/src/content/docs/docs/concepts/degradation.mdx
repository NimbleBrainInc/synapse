A Synapse app runs in any host that implements MCP Apps: Claude, ChatGPT, the
NimbleBrain runtime, or one you build. Hosts do not all offer the same things, and
each one says what it offers in its answer to `ui/initialize`, as
`hostCapabilities`.

Synapse reads that declaration once, when the app connects. Every method and hook
checks it before sending anything, and when a capability is missing the call does
one of three documented things:

- **No-op.** Fire-and-forget calls send nothing. Nothing on the other end would act
  on them.
- **`null` or silence.** Hooks that wait for the host keep their initial value, and
  callbacks never run.
- **`HostCapabilityError`.** Calls that return an answer reject **without
  sending**. A host that does not implement a request may never answer it, and
  Synapse's requests have no deadline, so sending anyway would leave your promise
  pending forever. The error's `capability` field names what was missing.

Nothing is gated on the host's name. A host that declares a capability gets the
call, whatever it is called.

## Per hook and method

| Hook / method | Needs | Without it |
| --- | --- | --- |
| `useTheme`, `useHostContext`, `app.theme` | nothing | Neutral defaults for the mode. Host-only context fields are `undefined`. |
| `useToolResult`, `useToolInput` | nothing | `null` until the host sends one. A host that mounts the app without a tool call never sends one. |
| `useResize`, `app.resize` | nothing | Always sent. The spec has no capability for it. |
| `useCallTool`, `app.callTool` | `serverTools` | `HostCapabilityError`. The hook's `error` holds it. |
| `app.readServerResource` | `serverResources` | `HostCapabilityError` |
| `useDataSync` | `serverResources.listChanged` | The callback never runs. The app shows what it last loaded. |
| `useModelContext`, `app.updateModelContext` | `updateModelContext` | No-op |
| `useSendMessage`, `app.sendMessage` | `message` | No-op |
| `app.openLink` | `openLinks` | Opens the URL with `window.open` instead. The same happens when the host refuses. |
| `downloadFile` | `downloadFile` | `HostCapabilityError` |
| `useCallToolAsTask`, `callToolAsTask` | `io.modelcontextprotocol/tasks` with `requests.tools.call`, under `experimental` | `HostCapabilityError`. Check `app.supportsTasks` first and fall back to `callTool`. |
| `useAction`, `action` | `ai.nimblebrain/action`, under `experimental` | No-op |
| `useFileUpload`, `pickFile`, `pickFiles` | `ai.nimblebrain/request-file`, under `experimental` | `HostCapabilityError` |
| `connect({ forwardKeys })` | `ai.nimblebrain/keydown`, under `experimental` | Keys are not captured, so the browser handles them as usual. |

## The portable subset

These parts of the surface are defined by the MCP Apps spec, and every host that
renders apps is expected to support them:

- the handshake, the host context and theme changes;
- tool input and tool results;
- calling your own server's tools (`callTool`);
- sending a message into the conversation (`sendMessage`);
- pushing what the user sees to the model (`updateModelContext`);
- reporting size (`resize`).

An app built only on these works the same in every host. Everything else in the
table above is still spec surface, but hosts may leave it out, so check the
declaration before you offer it.

## The NimbleBrain extensions

Three features have no equivalent in the spec. They are the NimbleBrain host's
own extensions, which Synapse implements a client for. Each has one name, used
as its method and as the identifier a host declares in
`hostCapabilities.experimental` to offer it. MCP Apps has no field for extensions, and
`experimental` is the only part of that object whose contents a spec client keeps.

| Extension | Method and declared identifier | Direction |
| --- | --- | --- |
| Host actions (`action`, `useAction`) | `ai.nimblebrain/action` | app → host notification |
| File picker (`pickFile`, `pickFiles`, `useFileUpload`) | `ai.nimblebrain/request-file` | app → host request, answered `{ files }` |
| Keyboard forwarding (`forwardKeys`) | `ai.nimblebrain/keydown` | app → host notification |

That is the complete list. `NIMBLEBRAIN_EXTENSIONS`, exported from the package
root, holds the same table in code.

Two NimbleBrain fields also ride inside spec messages, and other hosts ignore them:
the workspace in the host context, and the chat context on a `sendMessage` text
block, under `_meta["ai.nimblebrain/context"]`. Synapse sends the chat context only
when the host identifies itself as NimbleBrain (`app.isNimbleBrainHost`).

## Deciding what to offer

Read the declaration to decide what to show, rather than finding out from a no-op
or an exception:

```tsx
import { hostSupports } from "@nimblebrain/synapse";
import { useApp, useFileUpload } from "@nimblebrain/synapse/react";

function Attach() {
  const app = useApp();
  const { pickFile } = useFileUpload();
  if (!hostSupports(app, "requestFile")) return null;
  return <button onClick={() => pickFile()}>Attach</button>;
}
```

The spec capabilities are available as `app.hostCapabilities`, for example
`app.hostCapabilities.message`, and tasks as `app.supportsTasks`.
